Yes — if your target is a general-purpose Copilot/Kiro/Cursor-style agentic IDE, then we should deliberately not bake Java, Spring, PostgreSQL, AWS, or any other technology into the core architecture.

The right approach is to build a technology-agnostic coding agent platform where languages, frameworks, databases, cloud providers, and tools are discovered dynamically from the workspace.

8. Code intelligence

This is where your system becomes much more powerful than a simple chatbot.

You need a generic abstraction:

Code Intelligence API

For example:

find_symbol("UserService")

find_references("UserService.createUser")

get_definition("calculateTax")

find_implementations("PaymentProvider")

get_diagnostics(file)

get_dependencies(module)

Underneath, use language-specific implementations.

Code Intelligence API
                       │
       ┌───────────────┼─────────────────┐
       ▼               ▼                 ▼
    LSP layer       Tree-sitter      Indexer
       │               │                 │
       ▼               ▼                 ▼
   Language         Syntax          Repository
    Servers         Parsing           Graph

LSP is particularly important.

Instead of writing your own Java/Python/Go intelligence from scratch, integrate with existing Language Server Protocol implementations.

Then your agent gets:

Go → gopls
Python → Pyright/Pylance ecosystem
Rust → rust-analyzer
Java → Eclipse JDT LS
TypeScript → TypeScript language server
C# → OmniSharp/Roslyn ecosystem

Your platform consumes the common interface.

14. Memory

Workspace memory

What failed?
What remains?

What did the developer ask?

Architecture decisions

But don't dump all memory into every prompt.

The agent should not know:

"This is PostgreSQL."

"This is GitLab."

"I have a database tool."
